## 1. 两个阶段，不是两个 tab

工具有两个形态完全不同的界面，分属两个屏：

| | 排查台（case 屏） | 报告（report 屏） |
| --- | --- | --- |
| 主角 | 假设与分叉 | 结论与证据 |
| 时间轴 | `observedAt` | 由形态决定，未必有 |
| 可操作 | 放行 / 改写 / 拒绝 / 接管 | 只有导出 |
| 刷新 | 每秒都在变 | 定稿时冻结 |
| 失败的样子 | 拦不住、看不清在干嘛 | 看完还得问"所以是啥" |

两条时间线是同一批证据的两次投影，这是数据模型的事实，不该翻译成顶栏的两个 tab——排查线属于排查台，系统线属于报告。

**但两个屏共用同一套色板**——底色、语义色、字体完全一样，**差别只准来自密度、字号与留白**：排查台是拿来操作的，要密；报告是拿来读的，要疏。一深一浅会被读成两个应用，而这是同一个工具的两个阶段——报告里那句根因，和排查台里 ST3 的结论，本来就该是同一个东西。

## 2. 排查台：三区

```
┌ 顶栏  排查标题 · 状态计数 ·「N 项待你处理」· 计时/花费 · 接管 · 停止 ┐
│                                                                  │
│  轨道            证据区                  待办                     │
│  走到哪一步      这一步凭什么            哪些事卡在我这           │
│                                                                  │
└ 底栏  对话带（默认只露最后一句）+ 输入框 ──────────────────────────┘
```

**左·轨道**——主干纵向 + 分叉右生长，见 §3。
**中·证据区**——当前 step 的假设 / 证伪条件 / 结论，工具调用的原始输出 preview（命中行高亮），以及抽取出的证据行。
**右·待办**——所有需要人动手的事，按紧迫性分三级，见 §4。

对话被压到底部一条带，默认只显示最后一句 assistant 文本。agent 的文字里已经没有证据搬运，只剩判断，压缩掉不损失信息。

密度分层：轨道密（扫视用）、证据区疏（逐字读）、待办居中（要一眼看到边界）。

> 顶栏那格「计时 / 花费」是意图，尚未落地：`steps` 上有 `tokens` / `cost_usd` 两列，但还没有人读它们。

## 3. 轨道：主干永不重排

这是实时图唯一不可让步的约束。

> **主干严格纵向单调追加，永不重排；分叉只向右生长，分叉子树自己也遵守同一条约束。**

理由不是好看，是**新节点每几秒钻出来一个，任何"把图排漂亮"的布局算法都会让已有节点位移**——正读着第 3 个节点的证据，它跑了。代价是图越来越高而不是越来越宽，而纵向滚动本来就自然。

「不许回头改」不只管位置：**序号、缩进、会话断点也一样**。任何"等信息齐了再回来改写已渲染的那一行"都在这条禁令里。

**推翻关系用一条曲线回指**：被推翻的节点划掉并标「← 被 stX 推翻」，一条线从推翻它的节点弯回来。**全屏只有这一种曲线，它只表示推翻**——所以它一出现就不用读字也知道发生了什么。分叉因此只能靠缩进 + 「↳ 接 #N」认，不画连接线。

**推翻者不在这条轨道上时（跨案、或还没到），曲线画不出来，但划线照旧。** 少一条曲线只是少个指向，少一道划线则是把一个已经作废的结论显示成仍然成立的。

节点多到一定规模要折叠，折叠规则待真实排查验证后再定。

> 布局是纯函数 `renderer/track.ts` 的 `trackLayout()`，由 `npm run spike:track` 兜底；
> 它的实现约束（深度只从已出现过的父算、y 交给文档流、写入侧先归一认不得的父）写在那个文件里。

### 3.2 子 agent 泳道就是一次分叉

归属那半在 harness 侧（[overview](overview.md) §4.5），**轨道这半一行没改**：泳道的兜底步把 `parent_step_id` 指到起它那次调用所在的那一步，照旧按父子缩进。轨道不认识泳道，也不该认识——它只管"接在谁下面"。

- **缩进说不出「这是另一条 agent 在查」**，所以卡片上另有一枚**中性色**徽标。**不用暖色**：暖色是「需要人动手」的全局专属，一条支线在后台查东西并不找人
- **一条支线可能认不出自己的父**（桥比第一次工具调用晚到时）。那一行落在主干层，但徽标照旧——读的人看得出"这是另一条 agent 在查"，只是不知道接在哪一步。反过来把它当主干显示才是错的
- **支线的兜底步没有 `direction`，空文案要与主干那条不一样**：主干那句是「agent 在声明方向之前就先查了一次」，支线那句得说清方向由主线收敛时给——照抄主干那句的话，读的人会以为主线漏了一次 `open_step`
- **顶栏的「支线 N」与「进行中」是两枚独立的药丸。** 支线默认就在后台跑，主线这一轮收了之后它还可能在查。合成一个的话，界面要么把"只剩支线"说成主线在跑（停止按钮跟着冒出来，而它中断的是一轮已经收完的 turn），要么说成空闲
- **跑完的支线当场收口**，正文是**支线自己的话**。收口不是一种结论——那一步没有命题，`已证实` / `已推翻` 都无从谈起，所以它用中性色，也不进报告的任何一栏。留着不收的话，一条早就跑完的支线会永远显示成「进行中」
- **「停」长在那一行上，不在顶栏。** 顶栏那枚「支线 N」只说得出还剩几条，说不出要停的是哪一条。**只给还在跑的那几条显示**——停一条已经收尾的支线什么都不会发生，而按钮会让人以为发生了

## 4. 需要人的地方：按"不处理会怎样"分三级

不按工具类型分，因为工具类型不决定紧迫性。

| 级别 | 什么情况 | 不处理会怎样 | 提示强度 |
| --- | --- | --- | --- |
| ① 阻塞 | `ask_operator`：要人的凭据、或后果得由人担的（生产库、写操作） | 永远等下去。**这一档没有超时兜底**——自动填个假结果比等着更糟 | 实心暖色标头 + 顶栏计数，永远置顶（dock 角标是意图，尚未落地） |
| ② 限时 | `canUseTool` 闸门：范围过宽、动作可疑、方向不对 | 倒计时归零按预设放行，节点标记"自动放行" | 暖色描边 + 倒计时环，不抢焦点 |
| ②′ 接管 | 同上，但**开着接管模式**时挂上来的（[overview](overview.md) §3.5） | 永远等下去，同①档 | 同②档，但没有倒计时环，写「等你处置，不会自己放行」 |
| ③ 告知 | 只读类调用已自动放行 | 什么也不会发生 | 折叠成一行计数，中性色 |

> **②′ 不是第四档，是②档在接管模式下的形态。** 分出来只为记住一件事：这两档的全部分别就是
> 「不处理会怎样」，而接管模式恰好把它翻了过来——人刚说了每一条自己判，三分钟后替他放行
> 等于把这句话作废。**少了倒计时那张卡就与①档同形**，所以那句"等你处置"必须写出来：
> 留白读起来像它随时会自己过去。顶栏那个「已接管」同理要一直亮着——不显示的话，
> 人下次回到屏幕前看到的是一个"卡住不动"的 agent，而原因是他自己按下的那个开关。

**暖色是全局唯一的。** 界面里除了"需要人动手"，任何地方都不用暖色——余光扫过屏幕时，有没有事找你是一个颜色的有无，不需要读字。

**① 档四个字段的顺序是硬要求**：语句 → 预期 → 执行时间 → 结果。预期排在结果之前挡住事后合理化（D15）；执行时间不能省，它是这条证据进系统时间线的唯一凭据。语句可改，改后连同结果一起回传给 agent。

**① 档同时有多条时纵向排列共用一个提交动作**，不要逐条弹——批量问是提示词的事，批量答是界面的事。

**键盘要能全程处置**：`⌘↵` 提交回填 · `A` 放行 · `E` 改写 · `D` 拒绝并留话 · `J/K` 在待办间移动。切窗口执行 SQL 再切回来的成本已经很高，不该再加上找鼠标。

> 提交用 `⌘↵` 不是 `↵`：回填框要能粘多行结果，`↵` 得留给换行。`J/K` 落到一张①档卡上时直接把光标放进结果框——切窗口跑完 SQL 回来，下一个动作一定是粘贴。

## 5. 视觉纪律

能查清问题排第一。下面是硬线。

| | |
| --- | --- |
| 底色是四阶冷灰蓝，**不用纯黑** | `#0E1317` 代码块 / `#141A1F` 应用底 / `#1A2128` 面板与顶栏 / `#212A32` 选中。纯黑上的白字会晕，长时间看更累 |
| 语义色只有三个 | 成立 `#5A9EDD`（蓝，主色） · 推翻 `#C9564C` · 需要人 `#E0A94A`。不加第四个 |
| 每个语义色两档 | 描边档给排查台，正文档（同色相亮一级）给报告的大字。同一个颜色的两种用法，不是新颜色 |
| **蓝底不配黑字** | 深色界面里蓝色填充块必须配浅字。琥珀是例外——它本身够亮，配深字才对 |
| 色板全局一套 | 排查台与报告不分深浅两套，差别只能来自密度、字号、留白（§1） |
| 选中不用填色 | 用边框 + 极淡底色，填色会和语义色打架 |
| 对比度 | 正文对底 ≥ 7:1，次要 ≥ 4.5:1。语义色只做标记，不承载正文 |
| 字号有下限 | 节点里的假设句是要读的内容不是标签；日志等宽再小要眯眼，而那是全屏最需要看清的东西 |
| 全大写小标签 | 只用于分区名与状态词，绝不用于内容 |
| 不加纹理与扫描线 | 和等宽字打架，长时间看很累 |
| 只有两处动效 | 进行中节点的状态呼吸、倒计时环。其余不动 |
| 直角、无投影 | 层次靠 1px 分隔线与底色深浅，密度更高 |
| 状态一律写字 | 不用图标——截图分享出去时图标会失去含义 |

## 6. 报告页

单列长页，**没有 tab、没有折叠、没有内部滚动**。

这不是审美偏好，是被长图导出倒逼的：**凡是要点击才能看到的内容，截图里就不存在**（§7.2）。顶部那条是锚点导航——点击只滚动，不隐藏任何东西，导出时整条移除。

章节由形态组装，见 [overview](overview.md) §6.1.1。几条不该被改回去的：

- **每节右侧标注数据来源**（`投影 · ORDER BY occurred_at_ms` / `agent 生成`），让"哪些是投影、哪些是生成"对读者可见——这把 D17 变成用户能验证的承诺
- **被推翻的 step 强制留在「排查路径」里**（划掉 + 标注），不洗成一路顺利的叙事
- **通用四块永远在，空的写「无」**。整节消失读起来像"没这回事"，写「无」才是"查过，没有"
- **没收尾时报告是预览**，页首要说明形态还会变；收尾之后只认冻住的那个判断，事后没有入口再改

**系统时间线画成真正的时间轴：一条竖线 + 圆点**。这和排查台轨道是同一个母题，只是两条线的含义不同——轨道上是"我按什么顺序做的"（`observedAt`），报告上是"系统当时按什么顺序发生的"（`occurredAt`）。同一个形承载两条线，正好是本工具最核心的那组区别。竖线只在时间轴内部出现，与 §3 那条"全屏唯一的曲线表示推翻"不冲突：一个是直线连接、一个是曲线回指。

**圆点的填实 / 空心区分的是「这条证据出自的结论还成不成立」**——被推翻那一步给的证据照旧在列（结论可以被推翻，事实不会）。库里没有"关键事件"这个标记，不编一个。

> 章节的取舍是纯函数 `shared/report.ts` 的 `reportPlan()`，**报告屏与两种导出共用它**——
> 写两遍的必然结果是导出的那份和屏幕上的那份对不上，而报告是这个工具唯一交出去的东西。
> 由 `npm run spike:report` / `spike:markdown` 兜底，**改这一带之前先跑这两条**。

## 7. 两种导出，同一份章节组装逻辑

只是渲染目标不同。**两种并列一等（D26），按钮长一个样**——把其中一个做成次要按钮就等于替人选了一种。

**导出的内容要当不可信的处理。** 证据与结论全部来自工具输出与 agent，在界面上只是纯文本，进了 `.md` 就被当语法解释——而这份文档正是拿去到处贴的。转义不只为挡 HTML 注入：删除线与粗体在这份文档里**有语义**（划掉 = 结论被推翻、粗体 = 根因），伪造得出来就等于伪造结论。

**溯源字段（时间戳 / 锚点 / 工具名）一个字符都不能改**，包括折空白——它们是读者回查原始日志的依据，改一个字符就可能指到另一行。

### 7.1 Markdown

给会被继续编辑、被搜索、被贴进 PR 的场合。

- **根因用引用块置顶**——很多平台的预览只显示前几行，第一屏必须是结论本身
- **时间线用表格，不用 mermaid**——mermaid 在不少 wiki 和评论区不渲染，一旦不渲染就是一团噪音。mermaid 放进末尾 `<details>` 作为附加
- **证据用脚注**——正文只留 `[^e9]`，工具 / 锚点 / 时间戳来源统一落在文末索引，正文因此保持可读。⚠️ 多数渲染器只渲染被正文引用过的脚注定义，**漏引一条 = 那条证据在文档里整条消失**
- **被推翻的用删除线**——删掉就成了假历史
- **除那个 `<details>` 外全篇纯 Markdown**，保证到处都能渲染
- ⚠️ **GFM 会吃掉表格单元格首尾的空白**，这是格式的限制不是我们的选择——所以**文末索引才是溯源那一份**，表格是给人读的
- 时间轴的竖线圆点画不进 Markdown，这里退化成表格——这也是长图存在的理由之一

### 7.2 长图

给一贴进群里就要被看懂的场合。它不是报告页的截图，是报告页的另一个渲染视图（`?export=image`），共用数据与样式，去掉一切交互件。

| | |
| --- | --- |
| 宽度 | 1240 CSS px，@2x 输出 |
| 去掉 | 锚点导航、导出按钮、"展开全文"、任何 hover 才出现的东西 |
| 日志片段 | 只保留命中行 ±3 行并高亮；完整原文只在 app 与 Markdown 里给。**意图，尚未落地**——报告屏现在压根不印原文，证据只以结论与出处的形式出现，等真印了这一条要跟着一起做 |
| 页脚水印 | **每一页**都有：Case 编号 · 生成时间 ·「N 条证据可在 Inquestry 溯源」。长图会被转发到看不见上下文的地方，只有第一页带编号的话，被转走的那一页就是一段无从溯源的截图 |
| 分页 | 超长时按顶层小节切，**绝不从小节中间切断**；页眉带「Case 0417 · 2/3」 |
| 配色 | 与报告页一致，所见即所得。图片是这个工具的名片，不该长成另一副样子 |
| 不跟随系统主题 | 导出结果必须可预期：**同一个 case 在谁的机器上导出都是同一张图** |

**单页优先。** 多数排查应该压得进一张图；分页是超长时的退路，不是默认形态。如果经常分三页，说明该收的是内容不是尺寸。单页保持人选的文件名，分页才加 `-N`。

**打印是唯一的例外。** 深色页打印要么费墨要么被浏览器反色，该由 `@media print` 单独处理——换纸不换设计语言。屏幕、图片、纸是三种介质，只有最后一种需要单独一套。**意图，尚未落地**：现在直接打印报告屏仍是深底。

> ⚠️ **倍率不能交给 `capturePage()`**——它跟着当前显示器走，在 @2x 屏上开发会看到正好 2480px、
> 以为成了，而 1x 机器上悄悄少一半分辨率。上面那条"谁的机器上导出都是同一张图"是它的前提，
> 所以走 CDP 把 `deviceScaleFactor` 定死。这一带其余的实现约束（量排版的时机、分页与落盘的
> 全有或全无、回滚）都写在 `main/index.ts` 的 `exportImage()` 与 `renderer/ExportImage.tsx` 里。

## 8. 排查的一生

### 8.1 新建排查

顺序是**先选项目起点，再写问题**：

- **项目起点**（本地路径）—— agent 在这个目录下运行，继承该项目的 skill 与 MCP 配置（[overview](overview.md) §2）。给最近用过的路径做快捷入口
- **问题** —— 自由文本
- **基准日期** —— 见下。时区不收，取本机的
- **已知现象**（可选）—— 涉及服务 / traceId / 用户 ID / 报错码。填了能省掉 agent 前几轮试探，不填也能跑
- **Agent / 模型 / 思考强度** —— 落 `sessions` 不落 `cases`（D27）：一次排查跨多会话，中途换模型是常态（先用便宜的扫一遍，再换强的推）。放 case 层会让"这一步是哪个模型跑的"永远答不上来，而报告里要标它。effort **不是所有 backend 都有**——走 D19 的能力协商，不支持就整项隐藏，而不是给个假开关
- **权限模式初值** —— 分层放行（默认）/ 全程接管，随时可切

> **模型列表是问出来的，不是写死的。** `query.supportedModels()` 返回每个模型真实的 `supportsEffort` 与可用档位（实测 Haiku 一档都没有）。写死一张表就一定会在这里给出拧了不生效的假开关。代价是探测要 spawn 一次 CLI，所以带超时 + 缓存，问不到就退回内置表**并在面板上明说这是兜底**。

> **基准日期是硬需求，不是"可选线索"。**
> 日志时间串大多既没有日期也没有时区（`12:03:01.220`）。没有基准日期，`occurred_at_ms` 落不成绝对时刻，系统时间线就排不出来（[data-model](data-model.md) §2）。它由新建排查面板收集并落 `cases`，同时**写进首轮提问的正文**——harness 与 agent 两边补齐时间串的基准必须是同一个。
>
> 填错了不会报错，只会让系统时间线悄悄排乱。所以**提交前就校验**，并且**常驻顶栏**，不是填完就消失。

**时区不给用户填，取新建排查机器的本机偏移并落库定死。** 让人手填一个 `±HH:MM` 是把一个几乎总是同一个值的东西做成了一个能填错的空——填错的后果是所有无时区证据整体偏移几小时，而且没有任何报错。⚠️ 取的是**基准日期那一天**的偏移，不是此刻的（夏令时地区冬夏差一小时）。

> 代价要写明：**本工具因此假设「日志时区 = 创建排查那台机器的时区」。** 排查异地部署的系统时这条会错，错法是整条系统时间线整体平移。

**项目起点要在新建排查时就验**（存在、是目录、可读可进）。不验的话坏路径照样新建排查成功，要等点「开始排查」才由 SDK 抛错，而那时它已经进了最近目录列表。

**新建排查创建的是 Case 不是 Session。** 重开旧排查时以库里那份建单信息为准，本次不覆盖：基准日期一旦变过，已落库的 `occurred_at_ms` 就对不上了。**Session 要到真的跑第一轮时才开**——合在一起会让"打开 app 看一眼上次那次排查"每次都留下一条没有任何 turn 的空会话，还会污染"这一步是哪个模型跑的"。

**项目起点决定挂哪套工具**，不只是记录一个路径：填了就是真项目（`cwd` 指过去、加载该项目的磁盘 settings、直接给 Read/Grep/Glob 三件套），不填就是演示模式（隔离模式 + 内置玩具数据源）。把玩具数据源留在真项目里比没有它更糟——agent 会拿假订单日志当证据。

> 🔴 **"放开的是上下文不是权限"这句话是错的，实测推翻。** 磁盘 settings 里的 `hooks` 是一串 shell 命令，**加载即执行**：在一个只有 `.claude/settings.json` 的空仓库上新建排查，两个 hook 的命令都在宿主机上跑成了，没有任何提示，也不经过 `canUseTool` / `PreToolUse` / `disallowedTools`。项目 `.mcp.json` 里的 MCP server 同理，是直接拉起的进程。
>
> 所以工具面**只管得住 agent 自己发出的工具调用**。真正的信任边界是「你在新建排查面板里选的那个目录」，与在那个目录里直接跑 `claude` 等价。SDK 没有关掉磁盘 hooks 的开关（`managedSettings` 没有这一项），只有不加载那些 setting source 一条路。**已决定按"自己的仓库自己负责"接受该风险**（单人自用）。

#### 工具面：按后果分，判定交给 backend 的分类器

| 档 | 有哪些 | 怎么过 |
| --- | --- | --- |
| 直接放行 | 三个结构工具 · `ask_operator` · 记事本与工具检索 · 真项目下的 Read/Grep/Glob（演示模式换成玩具数据源） | 不记闸门，节点上不标 |
| 交给分类器 | **其余一切**，含 Bash、写盘、子 agent、数据源 MCP、联网 | 按后果判：删构建产物 / 写个临时脚本这类不惊动人；碰凭据、生产配置当场拒，agent 换手段接着查 |

原先是三档，第三档（一律不给）是 Bash 与写盘那几个。它挡住的不只是危险动作，还有**本机那些只读的查询 CLI**——而排查恰恰全靠它们（日志、`sentry-cli`、监控客户端多半都是 CLI 而非 MCP），于是每一条查询都要退成 `ask_operator` 让人贴结果。改成按后果分之后：

- ⚠️ **实测至今没见分类器把任何一次调用推给人**（`npm run spike:automode`），所以②档卡片在这条默认路上**不会出现**，被拒的调用是事后在轨道上看见的；想要"人当场放行"就按顶栏那个**「接管」**——那是②档卡片唯一的入口
- **这不是安全边界，是一道按后果判的默认值。** 真正的边界仍然是「新建排查时选的那个目录」（上面的红字）与"生产凭据不在本机"。`ask_operator` 因此没有贬值，只是定位变了：从"跑命令的唯一通道"变成**"要人的凭据、或后果得由人担的"**
- 闸门那套机器（②档卡片、改写、拒绝留话）**原样留着**：它是"人当场处置"唯一的入口

### 8.2 中途插话

四种方式，对应 [overview](overview.md) §3 的三档控制语义：

| 方式 | 语义 | 落到哪 |
| --- | --- | --- |
| 底部输入带 | 异步入队，**不打断** | 轨道插入一个「补充」标记节点，可撤回 |
| 选中某个节点再说 | 同上，但消息带 step 引用 | 补充挂在那个节点下，比全局输入框精确得多 |
| 拒绝并留话 | `deny + message`，turn 不中断（D6） | 该调用记为"被拒"，留话进节点 |
| 改写参数后放行 | `allow + updatedInput` | 记 `input_rewritten`，改后的语句一起回传 |

**被拒的调用节点上要看得见拒绝理由**——留话原样落 blob，它就是 agent 收到的那份工具结果。

> ⚠️ **撤回有粒度坑**（[overview](overview.md) §3.3）：多条排队消息合并成一个 turn 后，撤回非代表 uuid 是空操作，撤回批次代表 uuid 会丢整批，两种都报"未取消"。UI 要么不给批内单条撤回，要么明说"会连同这批一起撤回"。

### 8.3 并发多个排查

- **排查切换栏**：顶栏下面一排 chip，进行中的排在前面，各带一个徽标：等你 N（暖色）> 跑动中 > 已停 / 未打开 / 已定稿。切换不中断任何一个——main 持有全部运行时，renderer 只切投影
- **待办计数跨 case 全局汇总**（D28）。并发场景里最容易漏掉的一条：你在排查 A 上工作时，排查 B卡在 `ask_operator` 上等你；只在当前 case 显示的话那条支线会静静挂死。落法是每次排查的 chip 自带「等你 N」，顶栏另有一颗描边的「别的排查 N」，点它直接跳过去
- **活跃会话限流**：限的是真的 spawn 了进程的那些，不是载入的排查数。⚠️ **三种不能选：当前这个、正在跑的、挂着待办的。** 最后一条最容易漏——降级会把等着人回答的 pending 就地作废，等于替人做了「这条不查了」的决定，而 ①档故意没有超时兜底正是因为自动填个假结果比让人等着更糟。挑不出人选就让它超一个（软上限）
- **重开旧排查 = 新起一个 session**，`ordinal` 因此每个会话都从 1 重来，轨道上用「第 N 次会话」分隔线标出断点（只有一次会话时不标，那条线什么都没说明）
- **找旧排查就在这一排里搜**，不另开面板：心智是"上次那个从库延迟的"，下一步动作就是切过去，而切过去的入口本来就在这一排。三条要求：**排序与最近列表同一条规则**（不按命中条数排，否则同一次排查在这边第一那边第七，人会以为搜到的是另一个）· **摘要围着命中处取**且按来源优先级挑（问题 > 结论 > 方向 > 证据 > 支线 > 对话，否则一屏结果全是对话带里那句"好的我这就查"）· **结果要合上运行时那一半、且每帧兑一次**（「等你 N」只活在运行时里，冻在查出来那一刻等于废掉跨 case 汇总的全部理由）

> ⚠️ **切换是同步生效的，界面慢一拍。** main 一收到 `case:switch` 当时就换了当前排查，renderer 要等下一次快照才换屏，这中间旧界面照样发得出调用。**凡是作用在当前排查上的 IPC 都要带 renderer 那一屏的 caseId**，对不上就不执行。
>
> ⚠️ **「按 id 查表，查不到就自然安全」是错的**：查不到 = **静默什么都不做**，而两档的后果都不是无事发生——①档是人贴进去的结果凭空消失、回填挂到超时；②档更重，人按了「拒绝」却没落地，三分钟后按预设**自动放行**。所以**两个处置手势要回执成功与否**，没落地要说出来（那时卡片多半已经不在屏幕上，提示得挂在应用级）。
>
> ⚠️ **人敲进去的东西一律提到 App 级**，按「caseId + 条目 id」存——卡片跟着快照渲染，一换排查就卸载，局部 state 随之蒸发。

### 8.4 三种收尾，不是一个按钮

与 [overview](overview.md) §3「三档粒度不要混成一个 Stop 键」同源。

| 动作 | 对 agent | Case 状态 | 之后 |
| --- | --- | --- | --- |
| **停止** | 中断当前 turn，连排队消息一起清（D7） | `open` | 随时新开 session 接着查 |
| **定稿** | 先走完影响面与遗留问题两个强制 step（[overview](overview.md) §6.2） | `closed` | 冻结，只能导出 |
| **归档** | 同"停止"，外加标记放弃 | `aborted` | 仍可导出**半程报告** |

**提前终止不销毁任何证据**——与"结论可以被推翻，事实不会"（[data-model](data-model.md) §3）同一条原则。终止只做两件事：把挂起中的 pending 一律改判 `abandoned`（否则库里会攒下永远 resolve 不了的僵尸节点），给 Case 打上状态。

**半程报告的形态强制为未决型**：主体是排除矩阵与遗留问题，顶部明写"排查在第 N 步被人为终止"，**没有根因栏**。没查出来就是没查出来，不编——这比一份看起来完整实则半截的报告有用。

**缺强制 step 时不是报个错就完，而是把这两步派给 agent 去补**；就此收手走的是归档，那一档明写着放弃。

**冻结是真的冻**：`closed` / `aborted` 的排查不再新起会话、输入框禁用。不冻的话新步骤会追加到一个已下结论的排查上，报告与它记录的过程就此对不上。⚠️ **加了终态就要回头看一遍现有的动作有没有变成死控件**——错误横幅上那个「重开一轮会话」冻结之后点了毫无反应，留下错误本身、去掉按钮。

### 8.4.2 定稿那一下要选报告形态

定稿确认条上多一行五选一（D25，取值与主体块见 [overview](overview.md) §6.1.1）。它是**这一步唯一需要人做的判断**，也是 `cases.verdict_shape` 唯一的写入方。

- **摆在确认条里，不单开一屏。** 形态决定报告装哪几块，而"确认定稿"正是唯一看得见后果的那一下。拆开的话，人会在还不知道要选什么的时候先被问一次
- **预选值一路备好，人不动手也能一路按到底**：agent 声明过就预选它的，没声明就预选 harness 推断的，两者在选择条上分得出来（「agent 声明的」/「没人声明过，按现有数据推的」/「你选的」）。**来源标错等于替人认了一个判断**，所以"人动过手没有"要显式记，不能拿"当前值 ≠ 建议值"推
- **状态型没有应然/实然时压暗提示，但不禁用。** 那一对是它的报告主体，缺了这一块是空的，所以要在人按下去**之前**说。不禁用是因为人可能确实知道故障是这一类，而 agent 没填那一对——根因那一步已经收口了，它补不回来，禁掉等于把人堵死在一个它自己造成的缺口上
- **归档不给选**：半程报告一律未决型，盖掉 agent 声明过的任何形态

> 这一带最容易的失效方式是**不可逆手势用了过期的上下文**：确认条挂着的这段时间里，根因可能换人、排查可能被切走、强制 step 可能被推翻。所以形态与它的出处要一起冻、冻的那一份由后端带回来、执行时用弹出那一刻的 caseId。判断落在 `renderer/drafts.ts`，由 `spike:close` / `spike:cases` 兜底。

agent 那侧的对应负担只是 `close_step` 上多一个可选枚举。填了不生效的情形一律当场回警告——**清单以 `shapeWarnings()` 为准**（设计理由见 [tools](tools.md) §6.1），别在文档里抄一份，抄了就会实现补到五种而文档还写着三种。

## 9. 全量快照推送，不做增量 diff

main 每次领域事件后重算整个 `Snapshot` 推给 renderer（合流后再发）。

理由不是"数据小所以偷懒"，而是**增量 diff 的错法是静默的**：漏推一类节点，UI 上就是那类东西不存在，没有任何报错。等数据量真的顶不住再换增量，那时至少有个能对照的正确实现。

## 10. 运行环境的硬约束

装起来才暴露的一批，全部在 tsx spike 里不会出现：

| 约束 | 错法的表现 |
| --- | --- |
| **ESM preload 需要 `sandbox: false`** | 窗口全黑、无任何报错。Electron 只在关掉 sandbox 时加载 ESM preload，否则**静默失败** |
| **schema 必须幂等** | 第二次启动崩在 `table events already exists` |
| **case 只开一次，每次启动是它下面的新 session** | 否则 `UNIQUE constraint failed: cases.id`。这条崩溃反而印证了 Case > Session 分层是对的 |
| **schema / 提示词不能 `readFileSync` 读源码目录** | 开发期正常，打包必炸。schema 改成 TS 常量；提示词由构建期 `?raw` 内联 |
| **`canUseTool` 不是每次调用都到** | 白名单里没有 `Read`，它照样跑完。**闸门的入口是 PreToolUse**（§8.1） |
| **一个 inbox 只能配一个 query** | 点「重开一轮会话」后库里有了新 session、界面显示进行中，agent 却什么都没收到，全程不报错 |
| **一轮失败 ≠ 会话结束** | 凭据过期后界面显示「会话中」、主区空白。消息流**不会自己结束**，`for await` 不返回，状态永远停在 `live`。只能靠 result 消息的 `is_error` 判断，⚠️ **`subtype` 那时仍是 `"success"`**，信它必错 |

renderer 的报错默认只留在它自己的 devtools 里——`console-message` / `did-fail-load` / `preload-error` 三个事件必须转发到 main 的 stdout，否则每次都只能盯着黑屏猜。

## 11. 开发期自检

**两条现成命令，别自己拼**：跑全套自检 `npm run spike:all`，跑 app（含无人值守探针）`npm run app`。两者各自把 ABI 切好再跑——`better-sqlite3` 装完 Electron 之后只对一个 ABI 有效，而**忘了切的表现是 app 停在启动失败屏上干等到超时**。

harness 侧的记账、状态与投影由 spike 兜底，**改哪一带先跑哪一条**（清单看 `package.json` 的 scripts）。起真会话、靠订阅凭据的那几条不在 `spike:all` 里。

> ⚠️ **spike 打出 0 PASS / 0 FAIL 时先想 ABI，不是代码坏了**：脚本在 import 阶段就崩了，一条检查都没跑到，而计数看着像全过。

**renderer 的状态没有 node 侧的回归网。** 验它用**临时探针**：在 main 里加一段 env 开关的 `executeJavaScript` 脚本，驱动真 app（点按钮 → 读回 DOM），验完把探针删干净。能提成纯函数的（`renderer/drafts.ts`）就提出来进 spike。

无人值守跑一轮并截图（开关名与用法看 `main/index.ts` 里那段自检）：

```bash
INQUESTRY_AUTOSTART="<问题>" INQUESTRY_AUTO_OPERATOR=1 \
INQUESTRY_SHOT="a.png@25000,b.png@75000" INQUESTRY_SHOT_REPORT=report.png \
INQUESTRY_EXPORT_MD=report.md INQUESTRY_EXPORT_IMG=long.png \
INQUESTRY_SHOT_QUIT=1 npm run app
```

三条探针自己的坑，都实测过，且都是"安静地给出一个错答案"：

> ⚠️ **窗口未获焦点时 `capturePage()` 返回过期帧**（实测：点进报告屏后 400ms 拍到的与点击前**字节完全相同**）。固定等一会儿再拍是不够的——要留一帧点击前的，等画面真的变了才算拍到。**判断进度以库里的数据为准，不要以截图为准。** 同族的还有：`scrollIntoView({behavior:'smooth'})` 与 `ResizeObserver` 在未获焦点的窗口里一次都不跑——**这个 app 的验证环境天然不获焦点，凡是依赖帧的东西在那儿都验不出来。**

> 🔴 **"读界面上那条状态"的探针天生会串台**：两种导出接连跑时，后一段会立刻读到前一条还挂在屏上的回执，断言照样匹配，而它接着去核的产物**可能是上一轮留下的**——文件在、尺寸也对，全过，这一次导出却根本没跑。按下之前先关掉旧回执，并按 mtime 核产物是不是这次生成的。

> ⚠️ **`did-finish-load` 回调里抛出去的异常没人接**：表现是干等到超时、一行日志都没有。这一段要包 try/catch 并以非零码退出；**失败退出码不该被"成功之后要不要自动退出"的开关捎带决定**。

> **无人值守顺带暴露了一个真实观测**：建议答案对不上问题时（拿订单行去答"索引是什么"），agent 当场识破并拒绝把结论算作已验证——与 [tools](tools.md) §5 一致。
