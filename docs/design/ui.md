## 1. 两个阶段，不是两个 tab

工具有两个形态完全不同的界面，分属两个屏：

| | 调查台（case 屏） | 报告（report 屏） |
| --- | --- | --- |
| 主角 | 假设与分叉 | 判定与证据 |
| 时间轴 | `observedAt` | 由形态决定，未必有 |
| 可操作 | 放行 / 改写 / 拒绝 / 接管 | 只有导出 |
| 刷新 | 每秒都在变 | 结案时冻结 |
| 失败的样子 | 拦不住、看不清在干嘛 | 看完还得问"所以是啥" |

两条时间线是同一批证据的两次投影，这是数据模型的事实，不该翻译成顶栏的两个 tab——排查线属于调查台，事故线属于报告。

**但两个屏共用同一套色板**——底色、语义色、字体完全一样。差别只来自密度与字号：调查台是拿来操作的，要密；报告是拿来读的，要疏。

| | 调查台 | 报告 |
| --- | --- | --- |
| 正文 | 13.5px / 1.6 | 15.5px / 1.72 |
| 判定大字 | — | 26px |
| 页边距 | 14px | 60px |
| 小节间距 | 12px | 44px |
| 底色 / 语义色 | 完全相同 | 完全相同 |

一深一浅会被读成两个应用，而这是同一个工具的两个阶段——报告里那句根因，和调查台里 ST3 的判定，本来就该是同一个东西。

## 2. 调查台：三区

```
┌ 顶栏  案件标题 · 状态计数 ·「N 项待你处理」· 计时/花费 · 接管 · 停止 ┐
│                                                                  │
│  轨道 344px      现场 flex               待办 328px               │
│  走到哪一步      这一步凭什么            哪些事卡在我这           │
│                                                                  │
└ 底栏  对话带（默认只露最后一句）+ 输入框 ──────────────────────────┘
```

**左·轨道**——主干纵向 + 分叉右生长，见 §3。
**中·现场**——当前 step 的假设 / 证伪条件 / 判定，工具调用的原始输出 preview（命中行高亮），以及抽取出的证据行。
**右·待办**——所有需要人动手的事，按紧迫性分三级，见 §4。

对话被压到底部一条带，默认只显示最后一句 assistant 文本。实跑下来看的确实是节点：agent 的文字里已经没有证据搬运，只剩判断，压缩掉不损失信息。

## 3. 轨道：主干永不重排

这是实时图唯一不可让步的约束。

> **主干严格纵向单调追加，永不重排；分叉只向右生长，分叉子树自己也遵守同一条约束。**

理由不是好看，是**新节点每几秒钻出来一个，任何"把图排漂亮"的布局算法都会让已有节点位移**——正读着第 3 个节点的证据，它跑了。代价是图越来越高而不是越来越宽，而纵向滚动本来就自然。

实现上是定宽画布内的绝对定位：主干 x 固定，分叉整体右移一个缩进量，新节点只能出现在下方或右侧的空白处。

**推翻关系用一条曲线回指**：被推翻的节点划掉并标「← 被 stX 推翻」，一条线从推翻它的节点弯回来。**全屏只有这一种曲线，它只表示推翻**——所以它一出现就不用读字也知道发生了什么。

上限约 40 个节点，再多要折叠。折叠规则待真实案子验证后再定。

## 4. 需要人的地方：按"不处理会怎样"分三级

不按工具类型分，因为工具类型不决定紧迫性。

| 级别 | 什么情况 | 不处理会怎样 | 提示强度 |
| --- | --- | --- | --- |
| ① 阻塞 | `ask_operator`：生产库、敏感数据、写操作 | 永远等下去。**这一档没有超时兜底**——自动填个假结果比等着更糟 | 实心暖色标头 + 顶栏计数 + dock 角标，永远置顶 |
| ② 限时 | `canUseTool` 闸门：范围过宽、动作可疑、方向不对 | 倒计时归零按预设放行，节点标记"自动放行"（§3.6） | 暖色描边 + 倒计时环，不抢焦点 |
| ③ 告知 | 只读类调用已自动放行 | 什么也不会发生 | 折叠成一行计数，中性色 |

**暖色是全局唯一的。** 界面里除了"需要人动手"，任何地方都不用暖色——余光扫过屏幕时，有没有事找你是一个颜色的有无，不需要读字。

**① 档四个字段的顺序是硬要求**：语句 → 预期 → 执行时间 → 结果。预期排在结果之前挡住事后合理化（D15）；执行时间不能省，它是这条证据进事故时间线的唯一凭据（§5.1②）。语句可改，改后连同结果一起回传给 agent。

**键盘要能全程处置**：`↵` 提交回填 · `A` 放行 · `E` 改写 · `D` 拒绝并留话 · `J/K` 在待办间移动。切窗口执行 SQL 再切回来的成本已经很高，不该再加上找鼠标。

**① 档同时有多条时纵向排列共用一个提交动作**，不要逐条弹——批量问是提示词的事，批量答是界面的事（§5.1③）。

## 5. 视觉纪律

能查清问题排第一。下面是硬线。

| | |
| --- | --- |
| 语义色只有三个 | 成立 `#4FA898` · 推翻 `#C9564C` · 需要人 `#E0A94A`。不加第四个 |
| 每个语义色两档 | 描边档给调查台，正文档（同色相亮一级，如 `#6FC4B4`）给报告的大字。同一个颜色的两种用法，不是新颜色 |
| 色板全局一套 | 调查台与报告不分深浅两套，差别只能来自密度、字号、留白（§1） |
| 选中不用填色 | 用边框 + 极淡底色，填色会和语义色打架 |
| 对比度 | 正文对底 ≥ 7:1，次要 ≥ 4.5:1。语义色只做标记，不承载正文 |
| 正文字号 ≥ 13px | 节点里的假设句是要读的内容，不是标签 |
| 日志等宽 ≥ 11.5px | 再小要眯眼，而这是全屏最需要看清的东西 |
| 全大写小标签 9.5px | 只用于分区名与状态词，绝不用于内容 |
| 不加纹理与扫描线 | 和等宽字打架，长时间看很累 |
| 只有两处动效 | 进行中节点的状态呼吸、倒计时环。其余不动 |
| 直角、无投影 | 层次靠 1px 分隔线与底色深浅，密度更高 |
| 状态一律写字 | 不用图标——截图分享出去时图标会失去含义 |

密度分层：轨道密（扫视用，行高压紧）、现场疏（逐字读，给足行距）、待办居中（要一眼看到边界，用分隔带切开）。

## 6. 报告页

单列长页，**没有 tab、没有折叠、没有内部滚动**。

这不是审美偏好，是被长图导出倒逼的：**凡是要点击才能看到的内容，截图里就不存在**（§7.2）。顶部那条是锚点导航——点击只滚动，不隐藏任何东西，导出时整条移除。

章节由形态组装，见 [overview](overview.md) §6.1.1。每节右侧标注数据来源（`投影 · ORDER BY occurred_at_ms` / `agent 生成`），让"哪些是投影、哪些是生成"对读者可见——这把 D17 变成用户能验证的承诺。

被推翻的 step 强制留在「排查路径」里（划掉 + 标注），不洗成一路顺利的叙事。

**事故时间线画成真正的时间轴：一条竖线 + 圆点**，关键事件的点填实、其余空心。这和调查台轨道是同一个母题，只是两条线的含义不同——轨道上是"我按什么顺序做的"（`observedAt`），报告上是"系统当时按什么顺序发生的"（`occurredAt`）。同一个形承载两条线，正好是本工具最核心的那组区别（§1.4）。

竖线只在时间轴内部出现，与 §3 那条"全屏唯一的曲线表示推翻"不冲突：一个是直线连接、一个是曲线回指。

## 7. 两种导出，同一份章节组装逻辑

只是渲染目标不同。

### 7.1 Markdown

给会被继续编辑、被搜索、被贴进 PR 的场合。

- **根因用引用块置顶**——很多平台的预览只显示前几行，第一屏必须是结论本身
- **时间线用表格，不用 mermaid**——mermaid 在不少 wiki 和评论区不渲染，一旦不渲染就是一团噪音。mermaid 放进末尾 `<details>` 作为附加
- **证据用脚注**——正文只留 `[^e9]`，工具 / 锚点 / 时间戳来源统一落在文末索引，正文因此保持可读
- **被推翻的用删除线**——删掉就成了假历史
- **空的遗留疑点也要写**——写「无」比整节消失可信
- **除那个 `<details>` 外全篇纯 Markdown**，保证到处都能渲染
- 时间轴的竖线圆点画不进 Markdown，这里退化成表格——这也是长图存在的理由之一

### 7.2 长图

给一贴进群里就要被看懂的场合。它不是报告页的截图，是报告页的另一个渲染视图（`?export=image`），共用数据与样式，去掉一切交互件。

| | |
| --- | --- |
| 宽度 | 1240 CSS px，@2x 输出 2480px |
| 去掉 | 锚点导航、导出按钮、"展开全文"、任何 hover 才出现的东西 |
| 日志片段 | 只保留命中行 ±3 行并高亮；完整原文只在 app 与 Markdown 里给 |
| 页脚水印 | 每页固定：Case 编号 · 生成时间 ·「N 条证据可在 Inquestry 溯源」 |
| 分页 | 超过 6000 CSS px 按顶层小节切，**绝不从小节中间切断**，页眉带「Case 0417 · 2/3」 |
| 配色 | 与报告页一致，所见即所得。图片是这个工具的名片，不该长成另一副样子 |
| 不跟随系统主题 | 导出结果必须可预期：同一个 case 在谁的机器上导出都是同一张图 |

**打印是唯一的例外。** 深色页打印要么费墨要么被浏览器反色，由 `@media print` 单独处理——换纸不换设计语言。屏幕、图片、纸是三种介质，只有最后一种需要单独一套。

**单页优先。** 多数案子应该压得进一张图；分页是超长时的退路，不是默认形态。如果经常分三页，说明该收的是内容不是尺寸。

实现路径：离屏 `BrowserWindow({show:false, width:1240})` 载入导出视图 → 读 `scrollHeight` → `setContentSize` → `capturePage`。

> ⚠️ 必须等 `document.fonts.ready` 与一帧 `requestAnimationFrame` 再拍。`capturePage` 会返回过期帧，未获焦点的窗口尤其容易（§10 已踩过），不等就会拍到半成品。拍完比对图片高度与预期 `scrollHeight`，不符就重拍一次再报错——别默默产出半张图。

## 8. 全量快照推送，不做增量 diff

main 每次领域事件后重算整个 `Snapshot` 推给 renderer（60ms 合流）。

理由不是"数据小所以偷懒"，而是**增量 diff 的错法是静默的**：漏推一类节点，UI 上就是那类东西不存在，没有任何报错——duetlens 上「Discussion 栏整个为空却无人报错」正是这个形态。等数据量真的顶不住再换增量，那时至少有个能对照的正确实现。

## 9. 装起来才暴露的四个问题

前面四个 spike 全在 tsx 里跑，这些一个都不会出现：

| 问题 | 现象 | 结论 |
| --- | --- | --- |
| **ESM preload 需要 `sandbox: false`** | 窗口全黑、无任何报错 | Electron 只在关掉 sandbox 时加载 ESM preload，否则**静默失败**，`window.inquestry` 未定义、React 首个 effect 抛错整树卸载 |
| **schema 不幂等** | 第二次启动崩在 `table events already exists` | 全部 `CREATE ... IF NOT EXISTS` + `user_version`。投影可从 events 重放重建，所以迁移不必写数据搬运 |
| **case 每次启动都重开** | `UNIQUE constraint failed: cases.id` | 一次事故跨多会话（§4.1）：case 只开一次，每次启动是它下面的**新 session**。这条崩溃反而印证了 Case > Session 分层是对的 |
| **schema / 提示词用 `readFileSync` 读源码目录** | 开发期正常，打包必炸 | schema 改成 TS 常量；提示词由构建期 `?raw` 内联。两者都是启动必需品，这类失败只会在装机后才暴露 |

renderer 的报错默认只留在它自己的 devtools 里——`console-message` / `did-fail-load` / `preload-error` 三个事件必须转发到 main 的 stdout，否则每次都只能盯着黑屏猜。

## 10. 开发期自检

无人值守跑一轮并截图，用于没人盯着屏幕时验证 UI：

```bash
INQUESTRY_AUTOSTART="<问题>" INQUESTRY_AUTO_OPERATOR=1 \
INQUESTRY_SHOT="a.png@25000,b.png@75000,c.png@150000" \
INQUESTRY_SHOT_INCIDENT=incident.png INQUESTRY_SHOT_QUIT=1 \
npx electron-vite preview
```

`INQUESTRY_AUTO_OPERATOR` 用数据源给的建议答案代替人回填。**它同时暴露了一个真实风险**：建议答案对不上问题时（拿订单行去答"索引是什么"），agent 当场识破并拒绝把结论算作已验证——与 tools.md §5 观测到的行为一致。

> ⚠️ 窗口未获焦点时 `capturePage()` 可能返回**过期帧**，截图看起来"停在几十秒前"。判断进度以库里的数据为准，不要以截图的时间戳为准。同一个坑在长图导出里必须显式规避（§7.2）。

## 11. 当前欠缺

- **待办栏的两个控制手势还没接**：改写参数再放行、拒绝并留话。`canUseTool` 目前只做白名单，这是控制面最值钱、也是唯一没接的部分
- **轨道还是平铺卡片流**，未实现 §3 的主干 + 分叉
- **报告页还未拆成独立屏**，两种导出均未实现
- **原生模块要按运行环境重建**：`npm run rebuild:electron` 给 app 用，`npm run rebuild:node` 给 tsx spike 用；装完 electron 后 `better-sqlite3` 只对其中一个 ABI 有效
- 只有一个内置演示数据源，真实用法要接用户已有的 skill / MCP（overview §2）
- 对话带只存内存，不进库，刷新即丢
