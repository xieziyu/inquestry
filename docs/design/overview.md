# Inquestry 设计纪要

> 本文只写不随代码变的部分：产品定位、词汇、核心概念，以及几条来自外部实测的硬约束。
> 设计细节、界面规格、实现约束一律以代码与它旁边的注释为准；本文与代码有出入时，错的是本文。

## 命名与词汇

**Inquestry** = `quest-`（`inquiry` / `quest` 共用的词根：追寻、查证）+ `-ry`（一整套体系，同 registry / forestry）：查证记录的集合体。

- `quest-` 命中核心动作：提出一个可证伪的命题，再拿证据去查证它
- `-ry` 补上沉淀：单次追查是一次 inquiry，把每次追查积累成的档案体系才是 inquestry

名字会让人联想到 `inquest`（正式的事故调查程序），视觉基调因此偏探案——但**探案味只准出现在配色与排版上，产品文案一律走软件工程词汇**：调查 / 排查 / 结论 / 证据 / 根因 / 定稿，不用案件、立案、卷宗、疑点这类侦查词。

**Case 的中文是「调查」，它里面做的事才叫「排查」**：调查是可数的单位（一项调查、历史调查），排查是动作与由它构成的复合词（排查路径、开始排查）。

语义色是设计定死的封闭集，只有三个：**成立**（蓝，主色）· **推翻**（绯）· **需要人**（琥珀，全局唯一暖色——余光扫过屏幕时，有没有事找你是一个颜色的有无）。色值与其余视觉细则在样式代码里。

## 定位

日常已用 Claude Code 排查线上问题，定位准确度够用，但排查过程的中间态不可见、不可回溯。真正的问题不是 agent 说得太少，而是**证据在汇报环节被有损压缩了**：agent 读了 500 行日志，只写一句「主从复制延迟导致写入后读不到」，那 500 行没留存，复核只能重跑。

> **harness 负责把每一次工具调用的原始输入/输出完整落库；
> agent 的文字只做索引和判断，不承担搬运证据的职责。**

工具形态是实时交互（边排查边看、能及时打断换方向），Timeline 因此不是展示层，是**控制面**——节点上挂着可执行的操作（放行 / 改写 / 拒绝 / 接管 / 停止）。

## 核心概念

### 两条时间线

同一批证据的两次投影，不是两份数据：

| | 排查时间线 | 系统时间线 |
|---|---|---|
| 回答 | 我（agent）按什么顺序做了什么 | 系统当时到底发生了什么 |
| 排序依据 | agent 行动顺序（`observedAt`） | 事件真实发生时间（`occurredAt`） |
| 归属 | 工作区 | 报告 |

`EvidenceRef` 因此带双时间戳。系统时间线是 `ORDER BY occurredAt` 的投影，**不需要 agent 再写一遍**——让它凭记忆重述就回到了有损压缩，而且是在最重要的产物上有损。

### 数据层级

```
Case (一次调查) ── Session (一次对话) ── Step ── ToolCall ── EvidenceRef
```

一次调查经常跨多个会话，**检索维度是调查，不是会话**。事件全部落 SQLite（event sourcing）：append-only `events` 是唯一真相，投影表可重放重建，大 payload 内容寻址落盘。

### 三个工具（封闭集）

`open_step` / `close_step` / `ask_operator`，经进程内 MCP server 提供。**骨架显式声明、内容自动填充**：agent 只标步骤边界，期间所有工具调用由 harness 自动归属到当前步上，agent 完全不用复述输出。

`ask_operator` 是**权限边界，不是妥协**：要人的凭据、或后果得由人担的查询（生产库、敏感数据、写操作）永远不给 agent 直连；本机的只读查询 CLI 由 agent 自己跑——**按后果分，不按工具分**。`expect` 字段逼 agent 先说预期再看结果，挡住事后合理化。

### 结论可被推翻

真实调查里第 3 步的判断经常被第 7 步否掉。纯 append-only 的呈现会造出一条「一路顺利推导到真相」的假历史，而调查的价值恰恰在走错又折回的地方——所以结论支持被推翻（`superseded`），被推翻的步连同它的证据强制留在报告里。**结论可以被推翻，事实不会**：提前终止也不销毁任何证据。

### 报告是投影

报告的每一块都有确定的数据来源（时间线、根因、排查路径、影响面、遗留问题都从库里投影），报告与过程天然一致，改不了也编不了。Markdown 与长图两种导出并列一等，共用同一份章节组装逻辑。

agent 亲手写、没有投影来源的只有三处：未决型报告的「下一步怎么查」，以及下面两种**产出物**。查出根因的报告不留修复建议——方案由动手修的人评估，排查报告只交事实。

### 产出物

**形态回答「这次排查怎么推理的」，产出物回答「问的那个问题，答案是什么」**，两者正交：一份报告可以既是状态型、又交出一份名单。

有一整类调查的答案不是一段因果解释——「排查出这批小号」「哪些订单受影响」「是哪次变更引入的」——而是一组结构化事实。它们**跨多步聚合而来，没有任何一次工具调用的输出恰好就是它**，所以只能由 agent 亲手落一次账；这是 `expected` / `actual` 那一族字段的同类，不是证据。两种：

- **名单**：一组同类实体（userId / orderId / commit / apiKey）+ 口径。一条也算名单
- **指标**：一个带口径的数，住在影响面那一节里

**每种各有一个不许省的口径字段**（名单的「是不是全集」、指标的「是不是下界」）。它们才是这两个类型存在的理由：一列 id 与一个数字压成散文之后，最先丢的永远是这句话，而它决定读者敢不敢拿这份结果去动手。留成自由文本的话，agent 不写没有任何东西会提醒它，事后也没人看得出来少了什么——同 `occurredAt` 与 `ask_operator` 的 `expect`，字段存在是为了逼出那句最容易省掉的话。

## 订阅接入（外部实测事实）

**架构必须是「壳 + spawn 本机 `claude` CLI」**（`@anthropic-ai/claude-agent-sdk`），继承 `~/.claude` 的 OAuth 凭据走订阅额度：

- 不能自己写 HTTP client 打 api.anthropic.com
- 禁用 `--bare`——它强制 auth 走 API key
- `CLAUDE_CODE_OAUTH_TOKEN` 对 SDK spawn 出来的 CLI 无效（实测：明显无效的值照样跑通，而直接跑 `claude -p` 当场 401）。长效令牌这条路走不通，凭据只认钥匙串那一份

白送的能力：这样跑的 session 照常加载用户已有的 skill 与 MCP 配置，现成的日志查询、Sentry、代码检索能力不用重建。

## 信任边界

真正的信任边界是**新建调查时选的那个工作区目录**，与在那儿直接跑 `claude` 等价：磁盘 settings 里的 `hooks` 加载即执行 shell、`.mcp.json` 直接拉起进程，都不经过工具闸门（实测）。已决定接受该风险——单人自用，自己的仓库自己负责。
