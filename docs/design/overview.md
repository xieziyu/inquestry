## 0. 命名

**Inquestry** = `quest-`（`inquiry` / `quest` 共用的词根：追寻、查证）+ `-ry`（表「一整套体系 / 积累起来的集合」，同 registry / ancestry / forestry）。字面读作「查证记录的集合体」。

- `quest-` 命中核心动作——**为确立事实而系统地追查**：提出一个可证伪的命题，再拿证据去查证它
- `-ry` 补上另一维：**沉淀**。单次追查是一次 inquiry，把每次追查积累成的档案体系才是 inquestry——对应 Case 层、跨 case 检索、历史调查库

> 名字会让人联想到 `inquest`（正式的事故调查程序），这点底色是有意留的——**视觉基调偏探案**。
> 但**产品词汇一律走软件工程那套**：调查 / 排查 / 结论 / 证据 / 根因 / 定稿，不用案件、立案、卷宗、疑点这类侦查词。
>
> **Case 的中文是「调查」，它里面做的事才叫「排查」。** 调查是可数的那个单位（一项调查、历史调查、别的调查 2），
> 排查是动作与由它构成的复合词（排查路径、排查方向、排查时间线、开始排查）。
> 一度整个产品都叫「排查」，读不通的只有光杆当名词那几处——「还没有排查」「别的排查 2」「同时在跑的排查」——
> 因为 `排查` 在汉语里是纯动词，只有靠 `次` 才名词化；`调查` 名动兼类，两个位置都立得住。
> 「调研」否决：它指为决策做的摸底走访，不含诊断故障，而且新建面板的 placeholder 已经拿它指另一类任务。
> 探案味只准出现在配色、排版与那条"推翻"曲线上，不准出现在文案里。

## 1. 定位

### 1.1 要解决的问题

日常已用 Claude Code 排查线上问题——接入云日志服务（腾讯云 CLS / 阿里云 SLS）、Sentry 和代码仓库，再用一个自定义 skill 做编排。定位准确度够用，但排查过程的**中间态不可见、不可回溯**：

- 排查细节只在思考链或简短汇报里露出一点阶段性总结
- 想看「每一步在验证什么、执行了什么查询、原始输出是什么」非常麻烦
- 排查完成后无法沉淀成可复用的排查报告

### 1.2 第一性定位

> 真正的问题不是 agent 说得太少，而是**证据在汇报环节被有损压缩了**。
> agent 读了 500 行日志，只写一句「主从复制延迟导致写入后读不到」，那 500 行没留存，复核只能重跑。

由此：

> **harness 负责把每一次工具调用的原始输入/输出完整落库；
> agent 的文字只做索引和判断，不承担搬运证据的职责。**

Timeline 因此不是"日志美化"，而是**证据库 + 推理链的双层结构**。

### 1.3 Timeline 是控制面

工具形态是**实时交互**（边排查边看、能及时打断换方向），因此 Timeline 不是展示层，是控制面——**每个节点上要挂载可执行的操作**（放行 / 改写 / 拒绝 / 转后台 / 接管）。

### 1.4 两条时间线

设计分水岭，也是最终报告质量的关键。

| | 排查时间线 | 系统时间线 |
|---|---|---|
| 回答 | 我（agent）按什么顺序做了什么 | 系统当时到底发生了什么 |
| 排序依据 | agent 行动顺序（`observedAt`） | 事件真实发生时间（`occurredAt`） |
| 归属 | 工作区 | 报告 |

两条线是同一批证据的两次投影（[data-model](data-model.md) §3），不是两份数据。系统时间线**不需要 agent 再写一遍**——它是 `ORDER BY occurredAt` 的结果。

## 2. 订阅接入

**结论：能用订阅，机制与 codex app-server 一致。**

CLI 长驻双向流模式：

```bash
claude -p \
  --input-format stream-json \
  --output-format stream-json \
  --include-partial-messages \
  --forward-subagent-text \
  --include-hook-events \
  --replay-user-messages \
  --session-id <uuid>
```

stdin 喂 JSON 消息、stdout 吐事件流，长驻进程，多轮对话。上层用 `@anthropic-ai/claude-agent-sdk` 封装好的 spawn + 协议。

**授权边界（硬约束）：**

- SDK / headless 模式**spawn 本机 `claude` 二进制，继承 `~/.claude` 的 OAuth 凭据** → 走订阅额度
- **架构必须是「壳 + spawn CLI」**，不能自己写 HTTP client 打 api.anthropic.com
- **禁用 `--bare`**——它强制 auth 走 `ANTHROPIC_API_KEY` / apiKeyHelper
- **`CLAUDE_CODE_OAUTH_TOKEN` 对 SDK spawn 出来的 CLI 无效**（实测：明显无效的值照样跑通，而直接跑 `claude -p` 当场 401）。长效令牌这条路走不通，凭据只认钥匙串那一份

**白送的能力：** 这样跑的 session 照常加载用户已有的 skill 和 MCP 配置，现成的日志查询、Sentry、代码检索能力不用重建。

## 3. 控制语义

三档粒度差别很大，**UI 上对应三种不同手势，不要混成一个 Stop 键**。

### 3.1 一级：`canUseTool` —— 单次工具调用级

每次工具调用前回调到 UI，参数含 `toolName` / `input` / `toolUseID` / `agentID`（子 agent 来源，`undefined` 为主线）/ `title` / `displayName` / `description` / `suggestions` / `signal`。

> ⚠️ **"每次工具调用前"要打个折扣**——backend 觉得不用问就不会问，只读工具按默认模式直接放行，`canUseTool` 根本不到。真正每次都到的是 `PreToolUse` hook，**闸门的入口在那儿**（[ui](ui.md) §8.1）。

| 返回 | 效果 |
|---|---|
| `{behavior:'allow', updatedInput}` | **可改写参数再放行**——查询语句写窄了，直接改了让它跑 |
| `{behavior:'deny', message:'...'}` | 拒这一个调用，**把话带给 agent，turn 不中断**，就地换方向 |
| `{behavior:'deny', message, interrupt:true}` | 拒 + 停掉整个 turn |

> **关键决策：「打断当前方向、换个方向」用中间那行（deny + message）。**
> turn 的上下文全部保留，agent 收到纠偏就继续走。排查场景里前面几十轮的日志上下文重建成本极高，这个区别非常值钱。

### 3.2 二级：`interrupt()` —— turn 级（Stop 按钮）

杀整个 turn，连同所有子 agent。

- 返回 receipt，含 `still_queued`（会在这之后继续跑的排队消息 uuid）
- **Stop 按钮应传 `cancel_queued: true`**，一次性连排队消息清掉；否则按了停、队列里的东西照跑，体感是"没停住"
- 能力探测：`system/init` 的 `capabilities` 含 `interrupt_receipt_v1` / `interrupt_cancel_queued_v1`，需 feature-detect 而非版本嗅探

### 3.3 三级：异步消息入队 —— 不打断

turn 进行中往 stdin 塞 user message（带 uuid），可事后 `cancel_async_message` 撤回。语义是"我不拦你，但你这轮收尾时看一眼我的补充"。

**取消粒度坑：** 一批消息被 dequeue 并合并成一个 turn 后，取消**非代表** uuid 是 no-op（内容照跑），取消**批次代表** uuid 会丢掉整批。两种情况响应都报 `cancelled:false`。

### 3.4 子 agent 泳道的处置

- **支线默认就在后台跑。** `AgentInput.run_in_background` 默认为真：主线当场收到一条 `async_launched` 的 tool_result，turn 继续往下走，支线跑完再发 `task_notification`。**所以"折叠到后台"不是要提供的能力，而是默认形态**——要花力气的是反过来：让人看得见一条已经在后台跑的支线
- **能**把一条前台支线单独转后台：`backgroundTasks(toolUseId)` 只针对那一个调用（不存在的 id 返回 false）
- **能**单独停一条支线：`stopTask(taskId)` 当场停掉，回执 `status='stopped'`
- 停和转后台认的**不是同一个键**：转后台用 `tool_use_id`，停用 `task_id`，而 **`task_id` 就是那条支线的 `agent_id`**。`agent_id` 在支线第一次工具调用的 hook 里就有了，所以不必等回执、活着的时候就能停
- ⚠️ **被停掉的支线不发 `SubagentStop`**。凡是靠 `SubagentStop` 给泳道收尾的写法，遇到"人手动停了一条"就会让那条永远挂着——**收尾要认 `task_notification`**

「停」的入口在那条支线自己那张卡上（状态栏那枚「支线 N」说不出要停的是哪一条），认的是 hook 侧的 `agent_id`；**跑完的支线当场收口**，内容是它自己最后那句话。按下「停」不当场收口——被停掉的那条照样发 `task_notification`，收口只走那一条路。

### 3.5 接管模式（默认档叫「自动模式」）

全程每个调用都弹给人会累死，全程不管又来不及拦。因此默认只读类自动放行、拦截点放在方向变更处，另给一个一键「接管」的运行时开关。实现上：

- **入口是我们自己的 PreToolUse**，回 `permissionDecision: 'ask'` 把调用推到 `canUseTool` 上去，闸门卡就是这么来的。只能在这儿，因为 `canUseTool` 不是每次调用都到
- **backend 的 `permissionMode` 同时从 `auto` 切回 `default`**。只改前者的话分类器仍在判，而实测至今没见它把任何一次调用推给人（`npm run spike:automode`）——人按了「接管」，多数调用照旧到不了闸门上来。建会话与运行时切换共用同一个读数（`CaseRunner.permissionMode`），两处各写一份迟早说的是两回事
- **先等 backend 那侧切成，再落自己这边的状态**。fire-and-forget 的失败方式恰恰是这个开关唯一要防的：屏上写着「已接管」而分类器仍在判。连续切换要**串行化**，且"已经是这个状态了"的早退必须排到队之后再判——在入口处判读的是此刻的状态，而前一次切换可能还在飞
- **放行档不变**：结构工具、`ask_operator`、记事本与工具检索、真项目下的 Read/Grep/Glob 照旧直接过。读一次代码也堆成一张卡片的话，这个模式一开就没法用了
- 🔴 **接管那一档的闸门没有超时兜底**（§3.6 那条不适用于它）：人刚说了每一条自己判，三分钟后替他放行等于把这句话作废。它因此与 `ask_operator` 同形——等到有人处置，或这一轮被停掉为止。认的是**挂上来那一刻**在不在接管模式，不是处置那一刻
- **状态落 `case_ui_state`**：只存在运行时里的话，限流把这个 runner 降级一次、或关一次 app，"我要自己判"就被静默取消了——而那正是它要防的

🔴 **按后果分档的判定得自己在 PreToolUse 里做，不能外包给 `permissionMode: 'auto'` 的分类器。**
我们要的是"敏感写一定过人"这个保证，而这个保证只有自己判才给得出——分类器什么时候惊动人由它自己定，
它的行为随模型走、不随我们的设计走。**它到底拦不拦得住哪一类，以 `npm run spike:automode` 的实跑为准**
（那个脚本自己说明了两轮各在问什么、以及为什么"人点名要跑的命令被放行"不构成反例）。

配套的两条与分类器无关，是我们自己这侧的纪律：**记账不受权限模式影响**（auto 下 `PreToolUse` 照旧每次都到，
这是三档划法的地基）· **不能传 `allowedTools`**（裸工具名会在权限流之前整体放行，分类器与 `canUseTool`
都不会被问到，SDK 会打 `CAN_USE_TOOL_SHADOWED` 警告）。

### 3.6 ⚠️ 阻塞兜底（必做）

`canUseTool` 返回 Promise，**不响应就一直挂着，agent 干等**。所以默认路上必须有超时兜底：到点按预设策略走，并在节点上标记"自动放行"（时长是 `case-runner.ts` 的 `GATE_TIMEOUT_MS`）。

**两个例外，都是有意的**：接管档（§3.5）与 `ask_operator`（§5）**不设超时**——那两处人已经明说了自己判 / 结果只能由人给，替他放行等于把这句话作废。

### 3.7 `open_step` 的第二重价值：减速带

实时模式的硬约束：**agent 一个 turn 里可能并发甩出 5 个工具调用，等人看清在查什么，日志已经查完了。**

`open_step(direction)` 除了提供结构，更重要的是**在 agent 动手之前先把意图渲染出来**——看到的是"我怀疑是从库延迟，准备拉 create 前后 5 秒的主从日志"，而不是五个已经在跑的 query。这个几百毫秒到几秒的窗口，就是能有效介入的**全部窗口**。

## 4. 数据模型

### 4.1 层级

```
Case (一次调查) ─┬── Session (一次对话)  ── Step ── ToolCall ── EvidenceRef
  title        ├── Session
  status       └── Session
  report
```

一次调查经常跨多个会话（今天查一半明天接着查，或换个角度重开一轮），所以 session 之上必须有 Case 层。**检索维度是调查，不是会话。**

Claude Code 侧支撑：`--session-id` 指定、`--resume` 续接、`forkSession` 从某点分叉。

### 4.2 Step 节点

```
Step {
  id, parentStepId, lane          // 子 agent 用 parent + lane
  direction    : 这一步想验证的假设
                 （不是"我要查日志"，而是"我怀疑 X 导致 Y"——必须可证伪）
  actions      : ToolCall[]        // 自动采集，不需要 agent 复述
  verdict      : { text, confidence }
  evidenceRefs : EvidenceRef[]                                    ← ①
  status       : open | confirmed | refuted | inconclusive | superseded | converged  ← ②
  supersededBy : stepId
  t_start, t_end, tokens, cost
}
```

**① `evidenceRefs` 是「可溯源」的真正落点。**
结论光挂在节点上不叫溯源。agent 下结论时必须指明依据的具体位置，UI 上点结论就高亮原始输出的对应片段。没有这个字段，Timeline 只是把 agent 的话分了段，仍然无法验证它有没有编。

**② 结论必须可被推翻。**
真实调查里第 3 步的判断经常被第 7 步否掉。纯 append-only 的 Timeline 会呈现一条"一路顺利推导到真相"的假历史，而调查的价值恰恰在那些走错又折回的地方。UI 上第 3 个节点划掉并画一条回指箭头到第 7 个。

### 4.3 EvidenceRef（双时间戳）

```
EvidenceRef {
  toolCallId
  lineRange | jsonPath   // 溯源锚点：具体到第几行 / 哪个字段
  observedAt             // 我什么时候查到的    → 排查时间线
  occurredAt?            // 它描述的事件何时发生 → 系统时间线
  actor?                 // 谁 / 哪个组件干的
  claim                  // 这条证据说明了什么（一句话）
}
```

> **`occurredAt` 是本设计里最不能省的字段。**
> 有了它，系统时间线就是一次 `ORDER BY occurredAt` 的投影，**不需要 agent 再写一遍**；没有它，只能让 agent 在结尾凭记忆重述——那就回到了 §1.2 的有损压缩，而且是在最重要的产物上有损。

降低成本：日志类工具输出本来就带时间戳，harness 从返回结构里**自动抽取** `occurredAt`，只有人工粘贴的结果需要手填。

### 4.4 节点边界的产生方式

**骨架显式声明 + 内容自动填充：**

- agent 只负责标 `open_step` / `close_step` 两个语义边界
- **中间发生的所有 tool call 由 harness 自动归属到当前 open 的 step 上**，agent 完全不用复述输出
- `--include-hook-events` + PreToolUse hook 兜底：没有 open step 时的工具调用自动进「未归类」节点，不丢事件。⚠️ **这个兜底是常态路径不是保险丝**——agent 总是先查一次再 `open_step`

agent 的增量负担 ≈ 两次极短的 tool call，遵从性高；拿到的是完整结构。

可用 hook 事件（节选）：`PreToolUse` / `PostToolUse` / `PostToolUseFailure` / `PostToolBatch` / `SubagentStart` / `SubagentStop` / `TaskCreated` / `TaskCompleted` / `PermissionRequest` / `PermissionDenied` / `Stop` / `PreCompact` / `PostCompact`。

`PreToolUseHookInput` 带 `agent_id`（仅在子 agent 内触发时出现）和 `agent_type`——用它区分主线与子 agent 调用。

### 4.5 子 agent 呈现

lane key 用起子 agent 那次调用的 `tool_use_id`。**但记账口给的是 `agent_id`，两个键天生不同**，所以归属要过一座桥（`src/main/lane-bridge.ts`）：

- **活体桥是内层那次调用的 `tool_use_id`**：hook 侧有它（连同 `agent_id`），转发上来的子 agent 消息里也有它（连同 `parent_tool_use_id` = lane key），按它一 join，`agent_id ↔ lane` 就闭合了。**不要按到达顺序或"最近一次 Task 调用"去猜**——并发时支线的到达顺序会与发起顺序反过来，实测如此
- 支线**跑完之后**还有两条便宜的路，可用来对账、不能用来实时归属：Agent 的 tool_result（`tool_use_result.agentId`）、以及 `task_notification`（`task_id` 就是 `agent_id`）
- **桥没合拢时决不能回主干**：那次支线查询会记进主线正开着的那一步，报告里于是有一步的证据来自它从没发起过的查询，且没有任何报错。有 `agent_id` 就一定不是主干——桥没合拢就退回 `agent:<agent_id>` 这个临时 key，**且一个 `agent_id` 认过的泳道就不再改口**（晚一步升级 key 换来的是同一条支线裂成两步）
- **`forwardSubagentText` 只管子 agent 的正文。** 不开这个开关，子 agent 的 `tool_use` 块照样带 `parent_tool_use_id` 转发上来——**泳道归属不依赖它**
- Timeline 上泳道**不是一个新概念**：每条泳道各有一个「当前 open 的 step」，它的 `parent_step_id` 指到起这条支线那次调用所在的那一步，轨道于是照旧把它当一次分叉缩进（[ui](ui.md) §3.2）
- **支线不记账**：`open_step` / `close_step` 只有主线用得了，带 `agent_id` 的当场被 PreToolUse 回绝。MCP 那侧拿不到 `agent_id`，泳道传不进去——放它开步，那一步会落在主干上，主线随后的调用就记进一个支线开的步里
- **支线跑完由 harness 收口**：那一步落 `status='converged'`，正文取支线自己最后那句话。它不是一种结论——那一步没有命题——所以报告哪一栏都不进

### 4.6 持久化

- 事件全部落 **SQLite**，一行一 event，UI 从库**投影**出 Timeline（event sourcing）
- **不做内存态 + 事后 dump。** 反正要把事件解析一遍，增量成本接近零
- 白送三样：崩溃/断连恢复现场、多窗口看同一 session、导出排查报告
- 开 **FTS5** 全文索引 → 跨 case 检索证据

## 5. 人工回填通道（`ask_operator`）

调查中有些查询需要人工执行（特定数据库、Redis）：agent 给语句，人执行并回填结果。

**实现：** 用 SDK 的 `createSdkMcpServer` 建**进程内 MCP server**，不起子进程，handler 与 app 共享内存。

```
ask_operator({
  engine:    'mysql' | 'redis' | 'mongo' | ...
  env:       string   // 哪套环境 —— 与执行时间一起决定这条证据能不能被复核
  statement: string   // agent 给出的查询语句
  why:       string   // 为什么需要这条 —— 直接成为节点的 direction
  expect:    string   // 预期看到什么 —— 见下
})
```

handler 返回 Promise，UI 上出现一个 **pending 节点**，粘贴结果回来才 resolve。语义与其它工具调用完全同构，自动进 Timeline、自动成为 evidence。

### 5.1 设计要点

**① 语句必须可编辑再执行。**
agent 写的 SQL 表名字段名多半是猜的。改完之后**把改后的语句一起回传给 agent**——它就学到了真实 schema，后面几条不用再改。别只回传结果。

**② 粘贴框旁边要有 engine / env / 执行时间。**
这条证据要参与系统时间线重建，没有 `occurredAt` 就是孤儿。手工结果是唯一拿不到自动时间戳的来源。

**③ 批量问，别一条一条阻塞。**
提示词要求 agent 把需要人工执行的查询**攒成一组再发**，否则会在切窗口上耗掉一半时间。

**④ pending 期间 turn 的两种走法（都要支持）：**
- 还有并行支线 → agent 转去推进别的
- 没有并行支线 → 让这个 turn 收尾，回填后作为新一轮继续

**⑤ 重连要能 re-arm。**
SDK 要求客户端重连时 re-arm 尚未响应的 pending 请求（`initialize` 响应带 `pending_permission_requests`，且同一 `request_id` 可能同时以 live/replay 两种帧到达，**必须去重、只渲染一次**）。

### 5.2 定性：这是权限边界，不是妥协

> 生产库、敏感用户数据、任何写操作——**永远不给 agent 直连**，是有意的设计。
> 但范围是**按后果**而不是"一律"：本机上的只读查询 CLI（日志、`sentry-cli`、监控客户端）**由 agent 自己跑**。
> 原先把 Bash 整个关掉，代价是每一条查询都要人切窗口贴结果，而调查恰恰全靠它们。
> 这条通道只承担**要人的凭据、或后果得由人担的**那一类（D16）。
>
> agent 负责想清楚要查什么、为什么查、**预期看到什么**；人负责执行和把关。

`expect` 字段的作用：**逼 agent 先说预期再看结果**，挡住事后合理化（看到数据再倒推一个说法）。这是这套设计里少数几个直接提升结论质量的机制，也是敢把工具用在生产排查上的前提。

## 6. 最终报告

### 6.1 报告是投影，不是重写

每一块都有确定的数据来源：

| 报告章节 | 来源 |
|---|---|
| 系统时间线 | `evidenceRefs ORDER BY occurredAt` 自动投影 |
| 根因 | 最终 `status=confirmed` 的 step 的 verdict |
| 排查路径（含走错的） | step 树，含 `superseded` 分支 |
| 影响面 | 一个专门的量化 step（见 §6.2） |
| 修复建议 | **agent 唯一需要真正"生成"的部分** —— `close_step` 的 `remediation` |
| 遗留问题 | `status=inconclusive` 的 step 自动汇总 |

agent 只写最后两栏，其余是投影 + 一次润色。报告与过程天然一致，改不了也编不了。

> **修复建议挂 step 不挂 case**：建议是基于那一步的判断给的，那一步被推翻（`superseded`）
> 或假设自己被否掉（`refuted`）时它得跟着失效，否则报告里会躺一条基于作废判断的修复方案。
> 但**它不跟着根因走**——未决型与归档的半程报告压根没有根因，而"没查出来，下一步先加哪些观测"
> 恰恰是那种调查最该留下的东西。选择器因此是「最新一条仍然成立的声明」，只此一条
> （`queries.effectiveRemediation`）。

### 6.1.1 时间线只是五种结论形态之一

**系统时间线是报告主体（§1.4），但不是每次调查都有。** 配置写错、索引缺失、证书过期这类故障没有"事发瞬间"——故障状态一直存在直到被发现，硬凑一条时间线只会得到"某天变更、某天发现"两行，还会稀释掉真正重要的对照。

因此报告有**一块排在最前**，由形态决定：

| `verdict_shape` | 什么时候是它 | 排最前的那一块 |
|---|---|---|
| `sequence` 时序型 | 顺序 / 竞态错了，先后本身就是解释 | 系统时间线 |
| `state` 状态型 | 某个东西一直就是错的 | **应然 / 实然对照** |
| `distribution` 分布型 | 问题只压在某一小撮上，别的同类是干净的 | 归因切分 + 干净组对照 |
| `chain` 因果链型 | 其余一切，一处变更连锁放大 | 因果链（每环带置信度）+ 最弱一环 |
| `open` 未决型 | 没查出来 | **排除矩阵 + 遗留问题**，且没有根因栏 |

影响面 / 排查路径 / 遗留问题 / 修复建议四块在所有形态里都出现。

**形态只决定顺序，不决定取舍。** 其余几块各按自己的门槛补在主体之后，装得出来就装、装不出来就隐藏。一度是「每种形态硬丢掉另外几块」，已推翻：硬丢的代价是判错一次就少一整块，而定稿不可逆；现在判错的代价降成"重点排错了序"——写了 `chain` 而实际是时序型，系统时间线不会消失，只是排在因果链后面。

> **门槛不是"有没有数据"，是"装出来说不说得清一件事"。** 纯粹的有数据就装同样被否掉了：证据一律要填 `actor`，已证实的 step 也总是有的，于是归因切分与因果链的原料**恒定存在**——按那条写的话每份报告都会顶着这两块，而把十来条证据按 gateway / db / app 分个组，对绝大多数调查说明不了任何事。门槛写在 `shared/report.ts` 的 `block()` 里，那是唯一一处。

> 🔴 **归因切分是唯一保留"非主体不装"的一块。** 它的门槛数据里没有：证据的 actor 分布反映的是**agent 查了哪儿**，不是问题压在哪儿——查了 8 次网关、2 次库，网关那组自然最大，而这与"问题只在某一小撮上"毫无关系。只有 agent 说得出这句话。

> **根因栏另有一条**：未决型与归档的半程报告一律不装，哪怕库里正躺着一条已证实的结论。被归档的调查多半已经查出了点什么，按"有就装"写的话，明写着"没查出来"的半程报告会顶着一条根因。

> **主体块装不出来要写出为什么**（比如声明了 `state` 而根因那一步没给应然/实然），而不是默默少一节——它是形态承诺的那一块。**非主体块装不出来就静静隐藏**，那本来就是"有则展示、无则隐藏"的另一半。

> 🔴 **兜底兜的是形态，不是"这份报告一定有主体"。** 一次只有一条已证实结论的调查（没时间戳、没应然实然）会被推到终点档 `chain`，而链要两环才成立——五种主体这时一个都装不出来。**那种调查本来就没有"重点"这一块**，报告仍旧是根因加通用四块。所以别为了"凑一个装得出来的形态"去改推断，那只会让形态说一件数据不支持的事；纸头靠 `mainAssembled` 照实说，不会承诺一块不在的东西。

agent 的增量负担只是**多填一个枚举**，块的组装由 harness 做——D17「报告是投影」因此不动摇。

### 6.2 两个固化成流程的约束

**「影响面」是强制 step。** 排查经常找到根因就停了，但排查报告要回答"影响了多少用户、多长时间窗口"，这几乎总需要一次额外的聚合查询。做成定稿前的必经节点。

**「遗留问题」必须出现，哪怕是空的。** 现实里调查很少 100% 收敛，把没查清的部分明写出来，比一篇看起来严丝合缝的报告可信得多。

### 6.3 两种导出并列一等

同一份章节组装逻辑，两个渲染目标。详见 [ui](ui.md) §7。

- **Markdown** —— 给会被继续编辑、被搜索、被贴进 PR 的场合。根因用引用块置顶；时间线用**表格**而非 mermaid（mermaid 在不少 wiki 与评论区不渲染，不渲染就是一团噪音），mermaid 放进末尾 `<details>` 作为附加；证据用脚注，正文保持可读
- **长图** —— 给一贴进群里就要被看懂的场合。固定 1240 CSS px @2x，配色与报告页一致且不跟随系统主题（所见即所得，且同一个 case 在谁的机器上导出都是同一张图）

> **长图这条反过来定义了报告页的信息架构：凡是要点击才能看到的内容，截图里就不存在。**
> 所以报告的**纸**不能有 tab、折叠面板、内部滚动区——所有块必须平铺在一条纵向流里。这是 D22 的由来。
> **范围是纸，不是那一屏**：章节栏、交付台与导出预览都在纸之外，一个字都不进任何一份导出，不受这条约束
> （[ui](ui.md) §6）。

## 7. 决策清单

| # | 决策 | 理由 |
|---|---|---|
| D1 | 工具形态 = **实时交互**，边排查边看、能及时打断 | 核心诉求 |
| D2 | **Timeline 为主**；agent 与人说的话作为**节点织进轨道**，底部只留输入框与一条状态栏 | 看清每步 + 及时介入全发生在节点上。一度把对话压成底部一条带（只露最后一句），已推翻：判断没错，但那条带把判断摆在了离它所属的那一步最远的地方，读起来像一句悬空的总结（[ui](ui.md) §2） |
| D3 | 架构 = **壳 + spawn `claude` CLI**（Agent SDK） | 唯一能合规使用订阅额度的路径 |
| D4 | 禁用 `--bare` | 它强制走 API key |
| D5 | 节点边界 = `open_step`/`close_step` 定骨架 + 工具调用自动归属 | agent 负担最小，结构最完整 |
| D6 | "换方向"用 `canUseTool` **deny + message** | 保留 turn 上下文，避免重建成本 |
| D7 | Stop 按钮传 `cancel_queued: true` | 否则停不干净 |
| D8 | 权限**分层放行** + 一键接管 | 全拦太累，全放来不及 |
| D9 | `canUseTool` / `ask_operator` 必须有**超时兜底** | 否则 agent 干挂。例外是接管档与 `ask_operator`，见 §3.5 / §4 |
| D10 | 数据模型分四层：**Case > Session > Step > ToolCall/Evidence** | 一次调查跨多会话；检索维度是调查 |
| D11 | `EvidenceRef` 带**双时间戳** `observedAt` / `occurredAt` | 系统时间线的唯一来源 |
| D12 | Step 状态支持 `superseded` + `supersededBy` | 真实调查会推翻结论；append-only 会造假历史 |
| D13 | 事件落 **SQLite（event sourcing）+ FTS5** | 恢复/多窗口/导出/跨 case 检索，成本近零 |
| D14 | 人工查询用 `createSdkMcpServer` 自建 `ask_operator` | 进程内、UI 完全可控 |
| D15 | `ask_operator` 带 `expect` 字段 | 逼 agent 先说预期，挡事后合理化 |
| D16 | 生产库 / 敏感数据 / 写操作走人肉通道；**本机的只读查询由 agent 自己跑**（按后果分，不按工具分） | 权限边界是工具可用于生产的前提；而把 Bash 整个关掉会让每条查询都退成人肉回填 |
| D17 | 报告 = **投影 + 少量生成** | 避免二次有损压缩 |
| D18 | agent **知道**自己在被记录 | `open_step` 本身是显式的，无法隐藏 |
| D19 | agent backend **分三段抽象**：工具契约（MCP，天然跨端）/ 会话与事件流（接口）/ 控制语义（**能力协商，不是接口方法**） | 目标是 Claude + codex 两种 backend；核心结构全经 MCP 产生，落差全集中在控制语义。详见 [agent-backends](agent-backends.md) |
| D20 | 第一阶段**只实现 Claude backend，且不写 mock backend** | 空实现验证不了抽象；只守四条"事后补代价极高"的纪律 |
| D21 | 工作区与报告是**两个屏**，不是同屏两个 tab；但**共用同一套色板**，差别只来自密度与字号 | 人在两个屏前做的事不同，所以分屏；但一深一浅会被读成两个应用。详见 [ui](ui.md) §1 |
| D22 | 报告的**纸**是单列长页，无 tab / 折叠 / 内部滚动 | 由长图导出倒逼——点击才能看到的内容在截图里不存在（§6.3）。**约束的是纸不是那一屏**：纸之外的东西（章节栏 / 交付台 / 导出预览）不进任何一份导出；读成「整屏不许有要点击的东西」的代价是十来个控件全挤进顶栏一条 |
| D23 | 工作区舞台是**一整幅可缩放拖拽的画布**：**列 = 一条探索线，行 = 到达顺序，坐标只在节点出生时算一次、此后不再重算**；列号只往右发不回收。**唯一的例外是主干末端那张收束卡**，它的坐标每帧重算 | 实时界面里任何"排漂亮"的布局算法都会让已读节点位移，这是唯一不可接受的失败——所以画布上没有任何一步是"看一眼全局再排"。旧稿把这条写成"主干纵向追加 + 分叉只向右缩进"，缩进说不出"这一列是谁在查"，而列能：一条子 agent 支线自己就是一列，能往下长第二步。例外的判据是**位移会不会推走别人**：尾卡永远在所有盒子下方，它下移一张卡都碰不到。详见 [ui](ui.md) §3 与 §3.3 |
| D31 | 主干**有头有尾**：信息卡是头（问题），**收束卡是尾（结论）**，两张都是投影，不加第四个工具 | 没有尾的时候画布最低点永远是一句旁白，而 §1.2 定的分工是 agent 的文字只做索引和判断——让它当终点等于把结论交给一段可以说错的话。它在 agent 走定稿前那两个固定动作时出生（判据必须单调），在那之前调查还在跑，最低点是旁白并不是毛病。详见 [ui](ui.md) §3.3 |
| D24 | 需要人动手的事按**"不处理会怎样"分三级**，暖色为其全局专属 | 不按工具类型分——类型不决定紧迫性。详见 [ui](ui.md) §4 |
| D25 | 报告 = **一块由 `verdict_shape` 排到最前 + 其余块按门槛补**，时间线只是能排最前的几块之一；形态**由 agent 声明，人不参与** | 状态型故障没有"事发瞬间"，硬凑时间线会稀释真正的对照（§6.1.1）。形态要人在定稿时五选一那版已推翻：那次判断要读完整个排查过程才做得了，而最清楚过程的是 agent，人只是在一个理解成本很高的选项上替它按一下（[ui](ui.md) §8.4.2） |
| D26 | **Markdown 与长图并列一等**，共用同一份章节组装逻辑 | 两种分享场景都真实存在；只是渲染目标不同，不该做成两套内容（§6.3） |
| D27 | 新建调查时必须选**工作区目录**（落 `cases`），并收 **backend / model / effort**（落 `sessions`）；**基准日期与时区不问人**，建单那一刻取本机值落 `cases`，日期随后由 agent 读问题确认或改掉 | 工作区决定 agent 继承哪套 skill/MCP（§2），也是唯一的信任边界，所以它是这一屏的第一步而不是一个可跳过的选择；基准日期决定 `occurred_at_ms` 能不能落成绝对时刻，但它是"几乎总是同一个值、填错却毫无报错"的典型，让人填换不来什么——它该由读得懂问题描述的那一方定，而不是由建单那一刻的时钟定。agent 三项放 session 层是因为一次调查跨多会话、中途换模型是常态。详见 [ui](ui.md) §8.1 |
| D28 | 「等你处理」的计数**跨 case 全局汇总** | 并发调查时你在调查 A 上工作，调查 B卡在 `ask_operator` 上等你；只在当前 case 显示会让那条支线静静挂死。详见 [ui](ui.md) §8.3 |
| D29 | 收尾分**停止 / 定稿 / 归档**三档，`aborted` 调查仍可导出**半程报告**（形态强制 `open`）。**停止在工作区，定稿与归档在报告屏** | 与 §3「三档粒度不要混成一个 Stop 键」同源。终止不销毁证据，只把 pending 改判 `abandoned` 并给 Case 打状态。三档分属两屏是因为「停止」中断的是一轮，而「这份能不能交出去」只有看过报告才答得上。详见 [ui](ui.md) §8.4 |
| D30 | 调查标题由 **agent 读完问题描述后另起一次 spawn 生成**，人随时可改；建单那一刻先落一句由问题首行截出的兜底 | 问题描述是一段现象叙述（几十上百字、常带日志片段），截首行得到的是半截话——而列表、顶栏与导出文件名正是要一眼认出「是哪一次调查」的地方。详见 [ui](ui.md) §8.1 |

## 8. 已知风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **`occurredAt` 的强制规则设计错** | 头号风险：一刀切强制不会让字段变完整，只会让 agent 拿查询执行时间凑数，**假时间直接进报告主体** | 由 harness 按「本次调用是否真的产出带时间戳的记录」判定，不靠提示词自觉（[tools](tools.md) §3） |
| agent 忘记调 `open_step`/`close_step` | prompt 纪律不可靠 | PreToolUse hook 兜底进「未归类」节点 |
| 介入窗口过窄 | 并发工具调用来不及拦 | `open_step` 作为减速带 |
| pending 节点僵尸化 | 重连 / 重启后 resolve 不了 | 按 SDK 的 re-arm 契约恢复（注意 request_id 去重）；启动清扫把上一进程的 `pending` 一律改判 `abandoned` |
| 报告里洗掉走错的分支 | 会产出虚假的"一路顺利"叙事 | superseded 分支强制进报告 |
| 打包后 spawn 不到 `claude` | GUI 启动的 app 只有最小 PATH；签名后 entitlements 需允许子进程 | 显式指定可执行文件路径 + 补 PATH，详见 [architecture](architecture.md) |
| 原始输出撑爆库与 IPC | §1.2 要求完整落库，单次日志查询可达 MB 级 | 大 payload 内容寻址落盘、库存 hash + 可索引文本；IPC 只推摘要与 preview |
| codex backend 控制面弱一档 | D6 / 改写参数 / 运行时切档 / 泳道在 codex 侧无等价物 | 设计既定结果而非 bug，按能力协商降级。详见 [agent-backends](agent-backends.md) §4 |
| **仓库自带的配置是被信任的** | 真项目模式加载 `project` / `local` settings，其中的 `hooks` **加载即执行** shell、`.mcp.json` 直接拉起进程，三档工具面完全管不着（[ui](ui.md) §8.1 有实测） | 已决定接受：信任边界就是「新建调查时选的那个目录」，与在那儿直接跑 `claude` 等价 |
